# 1.8" TFT SPI Display - ST7735S

## What is a TFT screen?

A TFT screen is one of the types of displays we can use in electronics and Arduino projects. The size of these screens generally ranges from 1.44" to 3.2" and resolutions from 128x128 to 240x320 pixels.

Within the realm of home electronics, several TFT display models and drivers are available. Common examples include the ST7735 for sizes up to 120x160 pixels and the ILI9341 for sizes up to 240x320 pixels. Other drivers include the ILI9163C, the HX8357 (320x480px), and the Samsung S6D02A1 (QDTech).

In most cases, communication with the TFT screen is done via the SPI bus due to the high volume of data required. Therefore, they are easy to connect and use with Arduino.

Many of the available models include an SD or micro SD card reader, accessible via the SPI bus, which can be used to store images to be displayed on the TFT screen. There are also more expensive models that include a touch panel. If you're considering a touch panel, you should definitely look for a more powerful option.

## How does a TFT screen work?

A TFT display (Thin-Film Transistor Liquid Crystal Display) is an active-matrix LCD screen. It uses tiny transistors built directly into the screen’s pixels to control them individually. This technology allows for faster response times, sharper images, and much better color accuracy than older passive-matrix screens.

TFT screens are a variation of LCD (Liquid Crystal Display) screens. In general terms, an LCD is a glass panel that becomes opaque , and its opacity is electrically controlled.

LCD panels do not generate their own light; they require a backlight provided by a light source (such as fluorescent or LED). The LCD panel blocks the emitted light at certain points, allowing an image to be generated.

Here is the translation of the pin label to standard SPI terminology:

```
SCL -> SPI SCK (Serial Clock)
SDA -> SPI MOSI (Serial Data In / Master Out Slave In)
RST -> Reset (Hardware reset pin)
DC  -> Data/Command select (Sometimes labeled as RS or A0)
CS  -> Chip Select (Active LOW to enable the display)
BLK -> Backlight control (Can be tied to VDD or driven via PWM to control brightness)
```

Driving 128 x 160 color pixels requires pushing a massive amount of data compared to a tiny 128 x 64 monochrome OLED. If this were running over typical 400kHz I2C, the refresh rate would be painfully slow—essentially a slideshow. SPI allows you to crank the clock speed up to 15 to 30 MHz (or higher, depending on your microcontroller), giving you smooth rendering.

If you are setting this up with an ESP32-S3 using libraries like TFT_eSPI or Adafruit_ST7735, you will just map your chosen hardware SPI pins to SCL (Clock) and SDA (MOSI), and allocate three free GPIOs for RST, DC, and CS.

### BLK Pin (~2mA)
The BLK pin is just a control signal, not a power pin:
- BLK → R5 (1KΩ) → Base of S8050 transistor (U4)
- Base current ≈ (3.3V - 0.7V) / 1KΩ ≈ 2.6mA
- This tiny current just turns the transistor ON/OFF

### VCC Pin (~30mA)
The VCC pin powers everything:
- ST7735 LCD controller: ~5-10mA
- Backlight LEDs: ~20-25mA (flows through transistor U4)
- Total: ~30mA ✓

## Library

There are two primary libraries used to drive the ST7735 1.8" TFT display, each catering to different performance needs and controller types.

### 1. The Standard Choice: Adafruit ST7735 & GFX

This is the most common and "plug-and-play" option for Arduino users. It is well-documented but can be slower on more advanced microcontrollers like the ESP32.  

**- Required Libraries:** You must install both the "Adafruit ST7735 and ST7789 Library", the "Adafruit GFX Library" and "Adafruit BusIO" via the Arduino Library Manager.  
**- Initialization:** These displays often have a colored physical tab (black, green, or red) on the screen protector which indicates the specific software "initializer" needed (e.g., ```INITR_BLACKTAB```) to fix color inversion or pixel offsets.

## The are Two Types of Backlight Logic
The BLK (or LED) pin on your display module controls a transistor that powers the white LEDs behind the screen.  
*- Active HIGH* (#define TFT_BACKLIGHT_ON HIGH): Sending 3.3V (Logic 1) to the pin turns the backlight ON. Sending 0V turns it OFF. This is common on modules where the pin connects directly to the LED anode through a resistor, or uses an NPN transistor.  
*- Active LOW* (#define TFT_BACKLIGHT_ON LOW): Sending 0V (Logic 0) to the pin turns the backlight ON. Sending 3.3V turns it OFF. This is very common on cheaper modules that use a PNP transistor to drive the backlight.  

It's Active high for 1.8" TFP Display ST7735S.  

## The ESP32-S3 SPI Port Initialization Bug
In recent versions of the ESP32 Arduino Core (specifically versions newer than 2.0.14) and ESP-IDF, there is a known bug regarding how the default SPI port registers are mapped for the ESP32-S3. When TFT_eSPI tries to initialize the default SPI port (SPI2) during tft.init(), it can trigger a StoreProhibited exception or fail to communicate with the display, resulting in a white screen or continuous reboots.  
Even though your defined pins (MOSI=11, SCLK=12, CS=9) are the physical hardware pins for SPI2, the ESP32-S3 uses a GPIO matrix that allows any SPI controller to drive any pins. To bypass the register mapping bug in the newer ESP-IDF, you must explicitly tell the library to use the alternate SPI port.
The Fix:  
```cpp
#define USE_HSPI_PORT
```

## Font Types

### 1. Adafruit_GFX Library (Standard Adafruit)
The standard Adafruit library is much more basic out-of-the-box.  

Built-in Bitmap Fonts (1 Type):  
Font 1 (GLCD): It only has one built-in font: the exact same 5x7 pixel (8px high) font as TFT_eSPI's Font 1.  

How Adafruit handles "Sizes":
Because Adafruit only has one built-in font, it relies on the setTextSize(n) function to make text bigger.  
- ```setTextSize(1)``` = 5x7 pixels
- ```setTextSize(2)``` = 10x14 pixels
- ```setTextSize(3)``` = 15x21 pixels  

The Catch: This just stretches the original 5x7 pixels. It does not load a new, higher-resolution font. Therefore, large text in Adafruit looks very blocky and pixelated compared to TFT_eSPI's dedicated Font 2, 4, 6, or 8.  

Additional Font Types:  
- FreeFonts: Like TFT_eSPI, Adafruit also supports the 48 GFX FreeFonts, but you have to manually include the specific .h file for every single font you want to use in your sketch, which consumes a lot of RAM and Flash. TFT_eSPI handles this much more efficiently.
- Smooth Fonts: Adafruit_GFX does not natively support smooth/anti-aliased fonts without using heavy, unofficial third-party forks.

### 2. TFT_eSPI Library
TFT_eSPI is much more powerful when it comes to fonts. It has 7 distinct built-in bitmap fonts, plus support for 48 FreeFonts, and unlimited Smooth Fonts.  
As seen in Section 3 of the User_Setup.h, you can enable these built-in fonts by uncommenting the #define lines:  
Built-in Bitmap Fonts (7 Types):  
- Font 1 (LOAD_GLCD): The classic 5x7 pixel Adafruit font (8px high).
- Font 2 (LOAD_FONT2): A small, clean 16-pixel high font (96 characters).
- Font 4 (LOAD_FONT4): A medium 26-pixel high font (96 characters).
- Font 6 (LOAD_FONT6): A large 48-pixel high font (Numbers, ., -, :, a, p, m).
- Font 7 (LOAD_FONT7): A 48-pixel high 7-segment digital clock font (Numbers and ., -, :).
- Font 8 (LOAD_FONT8): A massive 75-pixel high font (Numbers only).
- Font 8N (LOAD_FONT8N): An alternative to Font 8, slightly narrower so 3 digits fit better on a 160px wide screen (Numbers only).

Additional Font Types:  
FreeFonts (LOAD_GFXFF): Gives you access to 48 different font styles (like FreeMono, FreeSans, FreeSerif in Bold/Italic/Regular).  
Smooth Fonts (SMOOTH_FONT): Allows you to load anti-aliased (smooth) TrueType fonts from the ESP32's flash memory (SPIFFS/LittleFS) or an SD card. These can be any size and any style you want.

### setTextSize(n)
When you use ```setTextFont()``` or ```setFreeFont()```, keep ```setTextSize(1)``` to avoid jaggies" or blocky, pixelated edges. Use large font type to get bigger font.        
Here is exactly how ```tft.setTextSize(1)```; impacts both:      
1. Impact on ```tft.setFreeFont(&FreeSans12pt7b)```      
   When using Adafruit FreeFonts, ```tft.setTextSize()``` changes the rendering scale factor, but it is highly recommended to leave it at 1.
   - Multiplier Effect: ```setTextSize(1)``` means the font renders at its native, pixel-perfect designed size (in this case, 12pt).
   - Scaling Behavior: If you were to change this to ```setTextSize(2)```, the library would multiply the vector glyph paths by 2.
   - The Catch: Because FreeFonts are rendered using a specific pixel-grid algorithm in these libraries, scaling them up (e.g., size 2, 3) often results in "jaggies" or blocky, pixelated edges.
   - Best Practice: If you need a larger Sans font, do not use ```setTextSize(2)``` on a 12pt font. Instead, keep ```setTextSize(1)``` and load a larger font file entirely, such as ```&FreeSans18pt7b``` or ```&FreeSans24pt7b```.    
2. Impact on ```tft.setTextFont(font_number)```
   When using internal/custom bitmap fonts (common in the TFT_eSPI library, where fonts are designated by numbers like 1, 2, 4, 6, 7, 8), ```setTextSize()``` acts as a strict pixel-doubling/tripling matrix.
   - Multiplier Effect: ```setTextSize(1)``` renders the bitmap font at its exact original pixel dimensions. For example, Font 2 is a small 16px high font; at size 1, it takes exactly 16 pixels vertically.
   - Scaling Behavior: If you change this to ```setTextSize(2)```, the library takes every single pixel of that bitmap font and draws it as a 2×2 block of pixels.
   - The Catch: While this makes the text larger without needing extra flash memory for a new font, it looks highly pixelated, blocky, and "retro."
   - Best Practice: For clean, crisp UI elements, keep ```setTextSize(1)``` and switch to a larger font number (e.g., moving from Font 2 to Font 4 or Font 6) if your library supports it. Use ```setTextSize(2)``` or higher only if you are constrained by flash memory or specifically want a pixelated look.     

### When TO Use setTextSize()
1. You are using the default/internal font: The default system font (often called Font 1 or the standard Adafruit GLCD font) is designed to be scaled. If you need a quick, readable header like "SYSTEM OK" or "MENU" and don't care about a "retro" or blocky look, changing ```setTextSize(2)``` or ```setTextSize(3)``` is the fastest, lowest-memory way to do it.
2. You are severely low on Flash Memory: If your code is at 95% storage capacity and you cannot afford to import a larger .h font file, ```setTextSize()``` is your only option to create visual hierarchy (making headers larger than body text).
3. You are changing text size dynamically: If you are creating an animation where text "zooms in" or pulses in size, you must use ```setTextSize()``` inside a loop to change the scale on the fly.
4. You want a "Retro" or Pixel-Art aesthetic: If your project has an 8-bit, cyberpunk, or arcade theme, scaling internal bitmap fonts up with ```setTextSize(2)``` or ```setTextSize(3)``` gives you perfectly blocky, nostalgic pixels.     

### ❌ When NOT to Use It (And What to Do Instead)
1. When you want smooth, professional UI typography: If you scale an Adafruit FreeFont (like ```FreeSans9pt7b```) to ```setTextSize(2)```, the vectors will look jagged, distorted, and unpolished.     
   Instead: Keep ```setTextSize(1)``` and include ```FreeSans18pt7b.h``` in your sketch.     
2. When rendering small text: Setting text size to fractional values (if supported by your specific library variation) or scaling down usually results in missing pixels and unreadable text.     
   Instead: Always design your base font to be the smallest size you need at ```setTextSize(1)```.

## RGB565 Format

Instead of the standard 24-bit RGB (8 bits per color = 3 bytes), RGB565 uses:
- Red: 5 bits (0-31)
- Green: 6 bits (0-63)
- Blue: 5 bits (0-31)
Total: 16 bits = 2 bytes (saves 33% memory!)   

The bit layout is: RRRRRGGGGGGBBBBB   
Breaking Down Examples:   
TFT_BLUE = 0x001F

```
Hex:     0x001F
Binary:  00000000 00011111
         ──┬── ──┬───┬─
           │     │   └─ Blue (5 bits)   = 11111 = 31 (max)
           │     └─ Green (6 bits)      = 000000 = 0
           └─ Red (5 bits)              = 00000 = 0
Result:   Pure Blue
```
TFT_GREEN = 0x07E0

```
Hex:     0x07E0
Binary:  00000111 11100000
         ──┬── ──┬────
           │     │   └─ Blue (5 bits)   = 00000 = 0
           │     └─ Green (6 bits)      = 111111 = 63 (max)
           └─ Red (5 bits)              = 00000 = 0
Result:   Pure Green
```

Conversion Formula:
To convert 8-bit RGB (0-255) to RGB565:
```cpp
// From 24-bit to 16-bit
uint16_t color565 = ((red   >> 3) << 11) |  // 8-bit → 5-bit, shift to bits 11-15
                    ((green >> 2) << 5)  |  // 8-bit → 6-bit, shift to bits 5-10
                    (blue   >> 3);           // 8-bit → 5-bit, stays in bits 0-4
```
Example for pure blue (0, 0, 255):

```
red   = 0   >> 3 = 00000 (0)
green = 0   >> 2 = 000000 (0)
blue  = 255 >> 3 = 11111 (31)

Result: 00000 000000 11111 = 0x001F
```
Why RGB565?
TFT displays like the ST7735 use RGB565 because:  
Saves memory: 2 bytes per pixel instead of 3  
Faster transfers: Less data to send over SPI  
Good enough: 65,536 colors vs 16.7 million (human eye can't tell the difference for most applications)  
The comment /* 0, 0, 255 */ in your code is just showing the equivalent 8-bit RGB value for reference, not the actual storage format!
